### Fixed

- **policies**: A provider that infers its joint-state ordering from the observation (the caller declared no `robot_state_keys`) now reads that ordering as positions only, in every provider rather than one. Every sim backend writes a velocity companion beside each joint position and documents it as an additive key position-only consumers are unaffected by, so the observation's insertion order alternates `[pos0, vel0, pos1, vel1, ...]`. The LeRobot provider dropped the paired velocity siblings before using that order; the Cosmos 3 provider inferred its order the same way and did not, so a 7-DOF arm's `joint_pos` request carried three rad/s readings in joint slots and never sent joints 5-7 - a worst joint error of 3.2491 rad, reported as sent. The rule now has one owner outside both providers, so two providers conforming to the same `Policy` contract cannot read one observation as two different state vectors. A declared `robot_state_keys` ordering is still never filtered - naming `elbow.vel` there states the model's input - and pairing is decided per key, so an unpaired `.vel` survives (LeKiwi's body-frame base velocities have no position companion).
