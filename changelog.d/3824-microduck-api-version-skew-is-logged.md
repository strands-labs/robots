### Fixed: `Robot("microduck", mode="real")` connects to a current robotd instead of refusing it over the Hello version number

`MicroduckDriver.connect_eagerly` refused any robotd whose Hello reply carried an `api_version` other than the driver's pin of 16, so a Microduck running today's robotd (which answers 28) was turned away before a single intent was sent, with "refusing rather than mis-parsing its frames". duck-ipc-proto's own rule is that no daemon refuses a call because this number differs: every bump since 16 added methods, and a call whose shape moved refuses itself by name on the one method that cannot be served. The driver now connects, logs a warning naming both versions when they differ, and reports the daemon's version in `get_status` as before. The pin moves to 28, the version this driver's frames were checked against, and `api_version` is refused at construction when it is not a positive integer, the same domain `subscribe_hz` already has, because both are interpolated into a JSON frame robotd decodes as a `u32`.
