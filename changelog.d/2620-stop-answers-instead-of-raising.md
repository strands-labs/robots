### Fixed

- **mesh**: a hardware stop that fails now answers instead of raising, so the emergency-stop accounting can see it. `Mesh._dispatch`'s `action="stop"` branch wrapped its two sim sub-paths -- "stop must answer, not raise" -- and left the hardware `stop_task` call bare. An exception escaping it reached `_exec_cmd`, which publishes `{"type": "error", "error": "dispatch error"}`; that envelope carries no `result`, so `_peers_that_did_not_stop` found neither `ok` nor `status` and `emergency_stop` counted the peer among its acknowledgements -- the arm whose stop failed was reported as halted. Raising was the only way a hardware stop could report failure, since both return paths of `Robot.stop_task` answer `status="success"`. The failure is now `{"ok": False, "error": "stop_task failed: ..."}` plus an ERROR log line, and the classifier's docstring census names all three reachable shapes.
